## Immutable ownership and upgrade behavior

The startup compatibility path now freezes branch ownership before legacy staff-pharmacy repair where historical records could otherwise drift. The relevant branch-local history includes:

- `shifts`
- `cash_movements`
- `daily_journals`
- `expenses`
- `financial_notices`
- `sales_invoices`
- `returns`
- `activity_log`
- `purchase_orders`

Known branch evidence is preserved. Where a legacy row is genuinely ambiguous, the conservative fallback is `local_default` rather than assigning it to a repaired/current staff branch.

Migration `022_finance_pharmacy_scope.sql` is intentionally a migration-ledger marker. The idempotent/table-aware compatibility and backfill logic lives in startup schema code so very old databases that do not yet contain later-version tables do not crash.

## Documented non-blocking architecture limitation

The generic Tauri renderer database bridge is not itself an authoritative branch security boundary. Normal application paths now supply/enforce the required pharmacy predicates, and no ordinary UI path was found that accepts raw SQL from a user. A compromised trusted renderer could still invoke the generic guarded write command or SQL read plugin outside business-domain authorization. The release build does not enable Tauri devtools and no normal devtools/UI SQL entry point was found.

Hardening this fully is a larger architecture change: Rust-side authenticated/domain-specific commands or equivalent SQL-aware authorization. A simplistic pharmacy filter in the generic bridge is unsafe because legitimate callers also manage global/master tables and schema compatibility operations.
