## Executive result

The v0.2.95 working tree passed the integrated application, TypeScript, lint, native Rust, migration and static-production-build validation performed in this audit. The final Jest run completed with **134 suites passed, 1 skipped; 1,060 tests passed, 2 skipped; 0 failed**. Native Rust validation completed with **46/46 tests passed**. TypeScript, ESLint and `git diff --check` passed, and the Tauri static production build generated **71/71 pages**.

The audit reproduced and corrected several material defects, mainly around pharmacy isolation, return/receipt visibility, financial reporting, unit-conversion history and cross-user UI state. The resulting fixes are regression-covered.

The application is a strong **local v0.2.95 release candidate** from the business-logic perspective. A signed updater/release is not yet fully proven: the local Tauri production packaging generated both MSI and NSIS installers, then updater signing stopped because `TAURI_SIGNING_PRIVATE_KEY` is not available in the local environment.

Production user data was not modified during this audit. Business-flow tests used isolated/in-memory databases, temporary native test databases and schema fixtures.

## Business-logic behavior verified

### Inventory, purchases and units

- Purchases create pharmacy-specific inventory and accounting effects.
- POS selected-unit sales deduct the corresponding fractional stock.
- Large/medium/small conversion round trips are covered natively.
- Historical conversion snapshots prevent later master-data edits from rewriting the meaning of past purchases or sales.
- Purchase returns validate the original invoice line, drug and available remainder.
- Duplicate purchase invoice lines within a return are rejected.
- Sales returns restore the original inventory batch and reject returns above the remaining sold quantity.
- Opening-balance input validation rejects invalid quantity/price/date values and snapshots current conversion data.
- Negative-stock settlement is scoped and accounted once.

### Financial flow

- Sale, return, purchase and purchase-return accounting paths are covered together with cash/card/credit behavior in the regression suite.
- Journals remain balanced in the native integrated purchase/sale/return lifecycle.
- Patient receivables count realized invoices and return/payment effects.
- Delivered invoices remain realized revenue after delivery state transition.
- Cash and handover reporting is pharmacy-scoped.
- Daily financial snapshots no longer collide between pharmacies.

### Permissions and tenant boundaries

- Owner/staff permissions and POS-specific permissions are covered.
- Return invoice selection now enforces return permission and pharmacy scope.
- Receipt drill-down no longer accepts a foreign-pharmacy invoice ID.
- Shared/open shifts are isolated by pharmacy.
- Staff and report read models have pharmacy-scope regressions.
- UI shortage handoff data is isolated by both pharmacy and user.

## Remaining architecture gaps / ambiguities

1. **Some master/financial entities remain chain-wide by schema.** Patients, suppliers and several financial/configuration resources do not carry a pharmacy identifier. Current behavior therefore treats them as shared resources. If the product requirement is strict branch-level isolation, this needs an explicit schema/product decision rather than scattered query predicates.

2. **Legacy daily snapshots cannot be historically split.** Old date-only aggregate rows did not contain branch identity. Migration 020 preserves them under `local_default`; there is no reliable data from which to reconstruct branch allocation.

3. **The daily snapshot field named `net_profit` is not formal accounting profit.** Its existing formula is a dashboard pulse based on sales/returns and net cash movements. The product should either rename it or define a formal profit calculation tied to revenue, COGS and expenses.

4. **The non-Tauri return path remains a fallback path.** It is now pharmacy-scoped and regression-covered, but the native critical command remains the authoritative desktop mutation path. The unused legacy general-return mutation function was removed.

## Coverage and environmental gaps

The audit is comprehensive across the repository's automated business logic and targeted UI regressions, but the following require environments or devices outside this local validation:

- Authenticode/updater signing and signed update install/relaunch/rollback/tamper testing.
- Clean disposable Windows 10/11 and Windows 7 VM install/upgrade/uninstall matrices.
- Authenticated staging Supabase/cloud synchronization and controlled network-failure scenarios.
- Physical receipt/label printers, barcode-scanner hardware and WhatsApp/external handler integration.
- Long-duration soak, low-memory/low-end hardware and multi-window concurrency stress.
- Full screen-reader, keyboard-only, DPI and accessibility matrix.
- Every possible click/field combination across all routes through a packaged desktop page-object E2E harness.

## Prioritized recommendations

1. **Resolve the remaining tenant-ownership schema decisions before expanding multi-pharmacy use.** Decide explicitly whether patients, suppliers and financial master data are chain-wide or branch-owned; return transactions now snapshot branch ownership.
2. **Complete the signed release gate.** Supply signing secrets through CI, generate the signed v0.2.95 candidate, validate the updater manifest and execute update/install/relaunch/recovery on disposable machines.
3. **Keep one authoritative mutation path for critical desktop operations.** The unused general-return mutation path is removed; continue routing production desktop returns through the native critical command.
4. **Add packaged desktop E2E for the highest-risk workflows.** Purchase → stock → POS → return, purchase return, credit/patient payment, shift/handover, shortage→purchase, receipts and permission denial should be driven through real UI controls on an isolated application profile.
5. **Improve test output signal.** Several UI suites still emit React `act(...)` warnings and intentional error-path logs. They do not currently fail tests, but removing test-harness noise will make future regressions easier to spot.

## Release-candidate assessment

For the code and business logic exercised locally, v0.2.95 is substantially more robust than the v0.2.94 baseline and the current automated/native validation is green. The main remaining release blockers are signed updater verification and environment-dependent installation/update/hardware tests, plus the documented product/schema decisions for chain-wide versus branch-owned master/financial data.
